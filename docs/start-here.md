**프론트매터 파서 수정 두 건도 배포됐다.** 빈 `tags:` 다음 줄의 `status:`를 값으로 물고

## ① 먼저 — 스코프 하나 추가하고 배포 (10분)

**낱말 두 개로 갈린다.**

```
확인    → 자리와 분류만 먼저 본다. PR은 안 열린다.
올려줘  → 그 한 번으로 PR까지 간다. 확인을 건너뛰어도 된다.
```

낱말을 안 붙이면 `확인`과 같다. `만들어라`·`넣어줘`·`PR`·`ㄱㄱ`·`그래`는 `올려줘`와 같다.

### 왜 고쳤나

어제 11:31과 11:45, 같은 명령(`만들어라` + 첨부)을 던졌는데 한 번은 PR이 열리고 한 번은
추천만 돌아왔다. 낱말을 잘못 읽은 게 아니다 — CloudWatch에 `tools=[search_wiki search_wiki
list_notes read_note read_note]`만 남았다. 모델이 `propose_note` 앞까지 오지도 않았다.
승인 검사(`goAhead`)는 그 툴을 부른 *다음*에 걸리는 문이라, 문 앞에 안 오면 아무 일도
일어나지 않는다.

모델이 그리로 굴러간 이유는 프롬프트의 홈이 한쪽뿐이라서였다. 확인 라운드의 출력 규격은
항목 다섯 개에 마지막 문장까지 통째로 인용해 적혀 있는데, 올리는 모드 규격은 한 줄이었다.
게다가 "초안을 다시 보내주세요"가 세 자리에 적혀 있었다. 약한 모델은 넓은 쪽으로 흐른다.

### 무엇을 고쳤나

판정을 모델에게 다시 시키지 않는다. 코드가 이미 `goAhead`로 읽고 있으니, **그 결과를 첫
메시지 끝에 통보로 붙인다** — `[코드 판정: 올리는 모드]` 또는 `[코드 판정: 확인 모드]`.
집행은 그대로 `runTool`의 같은 `goAhead`가 한다. 승인 없이 부르면 여전히 코드에서 막힌다.

정규식은 한 줄도 안 건드렸다. `확인`은 승인 낱말 목록에 없어서 그냥 기본값으로 떨어지고,
`만들어*`는 원래대로 PR 쪽에 남는다 — 그래서 11:31처럼 되던 건 그대로 되고, 11:45가
고쳐진다.

같이 붙인 것: 올리는 모드에서 "초안을 다시 보내달라"고 하지 말라는 금지, 그리고
**프론트매터 블록을 슬랙에 다시 찍지 말라는 금지.** 그 블록은 확인 라운드에서 "이렇게
심을게요"라고 미리 보여주는 것이고, PR이 열린 뒤에 또 적으면 뭘 더 해야 하는 줄로 읽힌다.
프론트매터는 `renderNote`가 파일에 심는다. 손으로 옮겨 적을 것은 없다.

`internal/brain/brain.go`(`verdict()` + 프롬프트 다섯 자리), `manual.go`, `propose.go`
(툴 설명·빈 본문 오류), `attach_test.go`, `propose_test.go`.

### 같이 들어간 것 — 스레드에 답글로 승인하기

같은 파일을 두 번 첨부하던 것을 없앴다. **첨부 + `확인`으로 자리를 본 다음, 그 스레드에
답글로 `올려줘` 한 마디만 달면 PR이 열린다.**

봇이 초안을 어디 저장해 두는 게 아니다. 파일은 슬랙에 그대로 남아 있으니, 승인만 온
메시지를 만나면 워커가 `conversations.replies`로 그 스레드를 다시 읽어서 그가 앞서 붙인
`.md`를 찾아온다. 그래서 메시지 하나가 곧 대화 하나인 구조는 그대로다 — 람다가 죽어도,
며칠 뒤에 답글을 달아도 같은 답이 나온다.

네 가지가 다 맞을 때만 스레드를 읽는다. 첨부가 없고, 넘긴 첨부도 없고, 스레드에 달린
답글이고, 올리라는 낱말이 있을 때. 승인 낱말은 `goAhead` 그 함수를 그대로 쓴다 — 목록이
두 벌이 되면 초안은 찾았는데 문은 안 열리는 날이 생긴다.

**되찾을 수 없는 경우가 하나 있다.** 초안을 파일이 아니라 **붙여넣기로** 보냈으면 다시
읽어올 방법이 없다 (슬랙에 남은 건 파일이지 글이 아니다). 그때는 본문을 `올려줘`와 같은
메시지에 붙여 다시 보내야 하고, 봇의 확인 답도 그렇게 안내한다.

**손일 — 스코프 하나가 필요하다.** 스레드의 앞 메시지를 읽는 권한이 지금 없다.

```
api.slack.com/apps → 그 앱 → OAuth & Permissions
  → Bot Token Scopes에 channels:history 추가
  → 위로 올라가 Reinstall to Workspace
```

디엠에서 쓸 거면 `im:history`, 비공개 채널이면 `groups:history`도 같이 넣는다.

재설치해도 **`xoxb-` 토큰 문자열은 대개 그대로다.** ⓞ에서 `files:read` 넣을 때 그것 때문에
한 번 헷갈렸다 — 스코프는 토큰 문자열이 아니라 슬랙 쪽에서 그 토큰에 붙는다. 화면에 뜬
토큰이 `.env`의 것과 다를 때만 편집기로 고친다 (`echo`로 덮어쓰면 개행이 붙는다).

스코프를 빼먹으면 조용히 실패하지 않는다. 봇이 스레드에 **"`channels:history` 스코프가
없어 보여요"**라고 적고, 지금 당장 올리려면 다시 첨부하라고 알려준다.

### 하나 — `layered-architecture.md` (옵시디언이 쓴 블록 꼴을 읽는가)

프론트매터가 블록 꼴이다 — 옵시디언에서 속성을 UI로 한 번 만지면 파일이 이렇게 다시
쓰인다. `aliases`와 `tags`를 내가 적었고, `updated`와 `status`만 비워뒀다.

```
@memories-bot 올려줘
```

볼 곳은 딱 한 줄, PR 본문의 **"봇이 채운 칸"**이다.

```
봇이 채운 칸: `status`                          ← 맞다. 두 수정이 다 올라갔다
봇이 채운 칸: `aliases` · `tags` · `status`     ← 둘째 수정이 안 올라갔다
```

아래쪽이 나오면 태그도 내가 적은 `cs/architecture, cs/layering`이 아니라 모델이 고른
것으로 바뀌어 있을 것이다. **이게 가장 위험한 실패다** — 경고도 없고, 옵시디언에서
일부러 뗀 태그가 PR마다 되살아난다.

옵시디언 문법 지적은 0건이어야 한다. 맨 위 `> 백엔드(NestJS / Spring) 관점...`은 그냥
인용문이니 세면 안 된다 — 콜아웃(`> [!info]`)만 센다.

그리고 오늘 고친 것이 여기서 같이 확인된다. **`올려줘` 한 번에 PR이 열려야 하고**, 슬랙
답변에 "초안을 다시 보내주세요"나 프론트매터 블록이 또 나오면 안 된다.

`topics/cs/README.md`의 목차를 깔끔하게 두고 싶으면 **PR #3을 먼저 머지**하는 게 좋다.
`lookup`은 `main`을 읽으니, 안 머지하면 두 번째 PR의 README가 첫 번째 PR의 목차 수정을
못 보고 다시 쓴다.

아직 한 번도 안 던졌다. 반대쪽 경로다 — 프론트매터도 옵시디언 문법도 아예 없고, 주제는

### 넷 — 스레드 답글로 승인 (두 번 첨부가 없어졌는가)

①의 새 경로다. 위의 셋 중 아무거나로 확인만 받은 뒤, **그 답이 달린 스레드에** 답글로:

```

```

파일은 다시 붙이지 않는다. 맞는 답: PR이 열리고, 슬랙 답 끝에 한 줄이 더 붙는다 —
**"*스레드에서 초안을 다시 읽었어요* — `파일이름.md`"**. 그 줄이 없으면 스레드를 안 읽고
그냥 본문 없이 굴러간 것이고, 그러면 "올릴 초안이 없어요"가 나와야 정상이다.

안 되면 봇이 이유를 적는다. **"`channels:history` 스코프가 없어 보여요"**면 스코프를 안
넣었거나 Reinstall을 안 한 것. **"not_in_channel"**이면 그 채널에 봇을 초대해야 한다.

세 파일은 볼트에 넣지 말고 슬랙에 던지기만 하면 된다. 위키 저장소에 untracked로
쌓이면 그것부터 정리해야 한다.

안 되면 어느 쪽이 문제인지 이렇게 갈린다. 봇이 파일을 **아예 못 본 척하면** 스코프가
반영이 안 된 것 — 십중팔구 Reinstall을 안 했다. 봇이 **"봇 토큰에 `files:read`
스코프가 없어 보여요"라고 답하면** 스코프는 갔는데 `.env`의 토큰이 옛것이다.
`slack post: invalid_auth`도 같은 원인이다.

```
(출력 규격 다섯 항목 대 한 줄, "초안을 다시 보내주세요"가 세 자리) 약한 모델이
그쪽으로 흘렀다.

판정을 모델에게 다시 시키지 않고, 코드가 이미 읽은 goAhead의 결과를 첫 메시지
끝에 [코드 판정: …]으로 통보한다. 집행은 그대로 runTool의 같은 goAhead가 한다.
정규식은 건드리지 않았다 — 확인은 승인 목록에 없어서 기본값으로 떨어지고,
만들어*는 PR 쪽에 남는다.

올리는 모드에서 초안 재전송 요청과 프론트매터 블록 재출력을 금지했다. 후자는
PR이 열린 뒤에 슬랙에 또 적히면 사람이 뭘 더 해야 하는 줄로 읽힌다.

프롬프트의 주장과 코드의 문이 갈리지 않는지 보는 테스트를 두 건 뒀다.
```

`internal/slackclient/replies.go` + `replies_test.go` + `client.go` +
`internal/jobs/job.go` + `cmd/bot/main.go` + `cmd/bot/thread_test.go` +
`internal/brain/propose.go` + `brain.go` 는 스레드 승인.

```
feat(slack): 스레드에 답글로 승인하면 앞 메시지의 초안을 다시 찾는다

같은 파일을 두 번 첨부해야 했다. 확인을 한 번 거치면 승인은 새 메시지를 타고
오는데, 메시지 하나가 곧 대화 하나라 그 메시지에는 초안이 없었다.

파일은 슬랙에 그대로 남아 있으니 다시 읽어 온다 — conversations.replies로 그
스레드를 훑어 그가 앞서 붙인 .md를 찾는다. 봇이 상태를 쥐는 게 아니라 슬랙을
다시 읽는 것이라 단발성 구조는 그대로다.

부르는 자리는 워커다. 게이트웨이는 3초 안에 ack해야 한다. 조회가 실패하면
조용히 넘기지 않고 거기서 끝낸다 — 넘기면 모델은 첨부가 없는 걸로 알고
"초안이 없어요"라고 답하는데 진짜 이유는 스코프다.

네 조건이 다 맞을 때만 부른다. 넘긴 첨부가 있을 때(.md가 아니거나 상한 초과)
안 부르는 게 중요하다 — 그는 새 파일을 올린 줄 알고 봇은 옛 파일을 올린다.

낱말 판정은 goAhead를, 파일 고르기는 jobs.Pick을 그대로 쓴다. 목록이 두 벌이
되면 어느 쪽이 틀렸는지 슬랙 답만 보고는 알 수 없다.

ThreadTS는 답을 올릴 자리로 쓰느라 빈 값을 TS로 메우고 있어서 답글인지
아닌지 구별이 안 된다. jobs.Job에 TS 한 칸을 더했다.

확인 모드의 마지막 줄도 고쳤다. 같은 파일을 다시 첨부하라고 시키던 자리다.
붙여넣기로 온 글은 여전히 본문이 한 번 더 와야 해서 그쪽만 갈라 적었다.

channels:history 스코프가 필요하다. 없으면 슬랙은 missing_scope 한 낱말만
주므로 무엇을 어디에 넣어야 하는지 사람 말로 바꿔 답한다.
```

`docs/`, `Deploy.md`, `test-drafts/` 는 문서와 테스트 파일.

```
docs: 확인/올려줘 짝 + 스레드 승인 + 다음 시작점 갱신
```

## ④ 그다음 — PR을 폰에서 읽기 좋게

**전에 추천했던 "검색 — 한국어 조사"는 취소다.** 손대려고 코드를 열었더니 이미 되어
있었다. `particles`가 조사 스물두 개를 떼고, 제목·alias 매칭이 본문 매칭보다 이미
무겁다. 실측으로 "동시성을 정리한 거 있어?"가 제목 맞는 노트에 10점, 본문만 스친
노트에 2점을 준다. 손댈 게 없다. `docs/next-steps.md` 1번도 그 내용으로 고쳐뒀다.

대신 이걸 추천한다. 지금은 PR이 열리면 스레드에 링크와 짧은 한마디만 간다. 폰에서
그것만 보고는 열어볼 값어치가 있는지 판단이 안 된다. 어디에 넣는지, 어떤 카테고리인지,
새 노트인지 기존 노트 수정인지, status와 태그가 뭔지 — 이 네댓 줄이 스레드에 같이
있으면 폰에서 바로 갈린다. 깃허브 앱 머지 버튼은 어차피 한 번 탭이라, 남은 마찰은
누르는 게 아니라 파악하는 쪽이다.

`propose_note`가 이미 구조화된 값으로 받아오는 것들이라 새로 알아낼 건 없다.
`internal/render`에서 한 번 더 풀어 쓰면 된다. 새 스코프도 새 권한도 없다.

순서상 ②를 먼저 하는 게 맞다. 첨부 경로로 PR을 열어보면 스레드에 뭐가 아쉬운지가
그 자리에서 보이고, 그걸 보고 시작하는 게 상상해서 만드는 것보다 낫다.
