# memories-wiki-bot

Slack에서 `@봇 요즘 뭐 정리했지?` 하면 내 GitHub 위키([`memories`](https://github.com/WoodrowDy/memories))를 직접 뒤져서 답하고,
공부한 초안을 던지면 **위키 규칙대로 정리해 PR을 열어주는** 봇. 머지는 사람이 한다.

| 단계 | 내용 | 상태 |
|---|---|---|
| 1단계 | 키워드 검색 — 멘션하면 노트를 찾아 경로·요약을 답한다 | ✅ 완료 |
| 2단계 | 자연어 브레인 — 모델이 툴을 골라 목록·본문을 읽고 답한다 | ✅ 2026-07-27 배포 |
| 3단계 | 쓰기 — 초안을 규칙대로 정리해 PR을 연다 | ✅ 코드 완료, 배포 대기 |
| 이후 | 슬랙 파일 첨부, 👍 머지, 검색 품질 | [아래](#다음-단계) |

## 지금 되는 것

```
Slack 멘션
  → API Gateway → gateway 람다 (서명 검증 → SQS에 넣고 즉시 200)
                     ↓ SQS
                  worker 람다 → Claude 툴 콜링 루프
                                 ├ search_wiki   키워드로 노트 찾기
                                 ├ list_notes    목록 훑기
                                 ├ read_note     본문 읽기
                                 ├ wiki_status   전체 통계
                                 └ propose_note  정리한 노트로 PR 열기
                              → 스레드에 답글
```

**묻는 모드**

- `@봇 동시성 정리한 거 있어?` → 검색 후 경로·status·요약·링크
- `@봇 요즘 뭐 배웠어?` → 목록을 훑고 최근 것들을 골라 요약
- `@봇 카프카 노트 요약해줘` → 본문을 실제로 읽고 요약
- `@봇 위키 현황` → 카테고리·성숙도·daily/personal 통계

**정리 모드** — 공부한 덩어리를 통째로 던지면:

1. `search_wiki`로 **같은 주제 노트가 이미 있는지 먼저 찾는다.** (있는데 새로 만들면 위키가 쪼개진다)
2. `docs/note-style.md`와 `CONVENTIONS.md`를 읽는다 — 정리 규칙은 봇이 아니라 위키가 갖고 있다.
3. 자리를 정한다: 기존 노트에 붙이거나(`update`), 카테고리를 골라 새로 만들거나(`create`),
   어디에도 안 맞으면 새 카테고리를 제안한다.
4. `propose_note` → `bot/note-…` 브랜치에 커밋하고 PR을 연다. 새 노트면 그 카테고리 `README.md`
   목차 링크도 같은 PR에 담는다.
5. 슬랙엔 "어디에 왜 넣었는지 + PR 링크" 두어 줄.

**아직 안 하는 것**: 슬랙 파일 첨부 읽기(지금은 붙여넣은 텍스트만), 머지, 이미지, 여러 사람 권한 분리.

**함수가 둘로 갈린 이유가 이 프로젝트의 핵심 제약이다.** 슬랙은 3초 안에 200을 못 받으면
같은 이벤트를 재시도한다. 그런데 모델이 툴을 두세 번 돌려 답을 만드는 데는 5~20초가 걸린다.
큐가 없으면 같은 답이 세 번 달린다. SQS가 그 경계다.
배포되는 바이너리는 하나이고, 들어온 이벤트 모양을 보고 자기가 gateway인지 worker인지 고른다.

**그 5~20초를 사람이 견디게 하는 게 "답을 쓰는 중…" 표시다.** 슬랙엔 봇이 보낼 수 있는
"입력 중…"이 없다 — `user_typing`은 봇이 *받는* 이벤트고 그나마 레거시 RTM 전용이다.
대신 `assistant.threads.setStatus`가 스레드에 같은 자리의 회색 표시를 띄운다. worker가
모델을 부르기 *직전에* 동기로 걸고, 답을 올리면 슬랙이 알아서 지운다. 못 올려도 2분이면
저절로 사라져서 표시가 스레드에 박히지 않는다. 실패해도 로그만 남기고 답은 그대로 나간다 —
진행 표시 하나 때문에 답을 못 주면 본말이 뒤집힌다.
[2026-03-05 변경](https://docs.slack.dev/changelog/2026/03/05/set-status-scope-update/)으로
`chat:write`만으로 호출되니 스코프를 새로 받거나 앱을 다시 설치할 일은 없다.

### 조용해지지 않는 3중 안전망

| 상황 | 동작 |
|---|---|
| `ANTHROPIC_API_KEY` 없음 | 1차 키워드 검색으로 답함 |
| Anthropic API 실패·과부하 | 키워드 검색으로 폴백 |
| SQS 전송 실패 | gateway가 그 자리에서 답함 (느리지만 답은 감) |

봇이 침묵하는 것이 가장 나쁜 실패다. 어떤 경로가 죽어도 답은 나가게 만들었다.
1단계 키워드 검색은 2단계가 들어왔다고 지워진 게 아니라, 폴백 경로로 그대로 살아 있다.

## 구조

```
cmd/bot/main.go          # 바이너리 하나, 이벤트 모양 보고 gateway/worker 자동 분기
internal/brain/          # 2단계 핵심 — 시스템 프롬프트 + 툴 정의 + 툴 콜링 루프
internal/llm/            # Anthropic Messages API 클라이언트 (stdlib만, 재시도 포함)
internal/queue/          # SQS SendMessage
internal/awssig/         # SigV4 서명 (AWS 공식 테스트 벡터로 검증)
internal/jobs/           # 큐에 실려가는 작업 한 건의 모양
internal/wiki/           # GitHub에서 memories 읽기 + 60초 캐시 + 경로 화이트리스트
internal/wikiwrite/      # 브랜치 생성 → 파일 커밋 → PR 열기 (머지 API는 없음)
internal/render/         # 키워드 폴백용 메시지 렌더링
internal/slackevents/    # 서명 검증 · 이벤트 파싱
internal/slackclient/    # chat.postMessage + assistant.threads.setStatus("쓰는 중" 표시)
internal/audit/          # 감사 로그
serverless.yml           # gateway + worker + SQS + DLQ
```

설계 원칙: **모델은 GitHub를 직접 만지지 않는다.** 다섯 개의 툴만 부를 수 있고,
각 툴은 자기 인자를 코드에서 검증한다. 경로는 프롬프트가 아니라 화이트리스트가 막는데,
읽기와 쓰기가 **일부러 다른 집합**이다.

| | 읽을 수 있는 곳 | 쓸 수 있는 곳 |
|---|---|---|
| `topics/ daily/ personal/ projects/` 아래 `.md` | ✅ | ✅ |
| `CONVENTIONS.md`, `docs/note-style.md` | ✅ | ❌ |
| 그 외 전부 | ❌ | ❌ |

규칙 문서를 읽을 수 있어야 그 형식대로 정리하고, 쓸 수 없어야 **자기가 지켜야 할 규칙을
스스로 고치지 못한다.** 반대로 카테고리 `README.md`는 쓸 수 있다 — 새 노트를 만들면서
목차를 같은 PR에서 갱신해야 하기 때문. 두 함수(`IsNotePath` / `IsWritablePath`)로 갈라 뒀다.

쓰기 쪽에 코드로 못 박은 것 셋:

1. 커밋은 `bot/`으로 시작하는 브랜치에만 간다. `main`에 쓰는 코드 경로가 없다.
2. **머지 API는 구현되어 있지 않다.** 봇은 PR을 여는 데까지고, 되돌리기는 "PR 닫기"로 끝난다.
3. 모델이 말한 `create`/`update`를 믿지 않고 **실제 repo 상태와 대조한다.** 어긋나면 거부하고
   어느 모드로 다시 부르라고 알려준다. 이걸 안 하면 기존 노트가 조용히 통째로 갈린다.

프론트매터도 모델이 아니라 툴이 만든다. `update`면 `created`를 보존하고, 태그·별칭은 합집합,
**status는 올릴 수만 있고 내릴 수 없다** — 모델은 습관적으로 `seedling`을 쓰는데 그대로 두면
초안 하나 합칠 때마다 evergreen 노트가 씨앗으로 되돌아간다.

루프에는 뚜껑이 있다: 최대 8턴, 응답 4096토큰, 노트 본문 8000자, worker 동시 실행 2개.
(마지막 턴은 툴을 뺏어서 모델이 답을 쓰게 만든다. 8턴은 정리 모드가 실제로 쓰는
검색 → 규칙 문서 2개 → 목차 → 기존 노트 → PR → 마무리에 맞춘 값이다.)

## 비용

기본 모델은 `claude-haiku-4-5` ($1 / $5 per MTok).

- **묻는 모드**: 2~3턴, 입력 3~8k → **질의당 약 $0.01**. 하루 20번 물어도 한 달 몇 달러.
- **정리 모드**: 초안이 턴마다 다시 실려 가서 입력이 제곱으로 붙는다.
  5,000자 초안 기준 **한 건에 약 $0.08(≈110원)**, 기존 노트까지 읽으면 $0.11 정도.
  초안이 두 배면 비용도 두 배다.

`maxTokens`를 4096으로 올린 건 비용과 무관하다 — 출력은 실제로 생성한 만큼만 청구되므로
짧은 답의 비용은 그대로고, 저건 폭주 방지용 뚜껑이다.

아직 안 당긴 절약 레버 둘: (1) 게이트웨이에서 정리 요청을 알아채 규칙 문서 두 개를 시스템
프롬프트에 미리 실으면 왕복 2턴이 사라진다. (2) 프롬프트 캐싱을 붙이면 고정 앞부분의 입력
비용이 약 1/10이 되어 정리 한 건이 $0.02 수준으로 내려간다. **실제 감사 로그 숫자를 보고
결정한다** — 지금 넣으면 어디가 비싼지 모른 채 복잡도만 는다.

AWS 쪽(Lambda·SQS·API Gateway)은 이 정도 트래픽이면 프리티어 안에서 논다.

## 네가 할 일 — Slack 앱 만들기 (봇 유저)

> 지금 Cowork에 연결한 'Slack 커넥터'와 **별개**. 이건 채널에 상주할 *네 봇*을 만드는 것.

1. https://api.slack.com/apps → **Create New App** → From scratch. (개인 테스트 워크스페이스 권장)
2. **OAuth & Permissions → Bot Token Scopes**: `app_mentions:read`, `chat:write` 추가 → **Install to Workspace** → `xoxb-...` **Bot User OAuth Token** 확보.
3. **Basic Information → Signing Secret** 확보.
4. **Event Subscriptions → Enable** → Request URL에 배포된 `https://.../slack/events` 입력(서명시크릿 설정 후 검증 통과). **Subscribe to bot events → `app_mention`** 추가 → 저장.
5. 채널에 봇 초대: 대상 채널에서 `/invite @위키봇`.

## 빌드 · 배포

```bash
go vet ./... && go build ./... && go test ./...

cp .env.example .env      # 처음 한 번만 — 시크릿을 채운다

./deploy.sh               # .env 로드 → vet·test 게이트 → arm64 빌드 → deploy
```

`.env`에 채울 것: `SLACK_SIGNING_SECRET`, `SLACK_BOT_TOKEN` (필수),
`ANTHROPIC_API_KEY` (없으면 키워드 모드), `GITHUB_TOKEN` (선택, rate limit 완화),
`GITHUB_WRITE_TOKEN` (없으면 PR을 못 열고 질문에만 답한다).

> **쓰기 토큰은 읽기 토큰과 반드시 다른 토큰이어야 한다.** 그래야 읽기 클라이언트가
> 쓰기 권한에 손댈 방법이 없다 — 타입까지 갈라 놨으니 코드로도 못 닿는다.
> fine-grained PAT를 `memories` 하나에만 걸고 **Contents = R/W, Pull requests = R/W,
> Metadata = Read-only** 딱 셋만 켠다. Administration·Actions·Workflows는 켜지 않는다.
> 발급받은 값은 터미널에서 `.env`에만 넣는다 — 채팅에도 깃허브에도 붙여넣지 않는다.

배포 후 나온 HTTP API URL + `/slack/events`를 4번 Request URL에 등록.
다른 위키를 쓰려면 `WIKI_OWNER` / `WIKI_REPO` / `WIKI_BRANCH` 환경변수로 교체.
자세한 절차와 막혔을 때 확인할 것들은 [Deploy.md](Deploy.md)에 있다.

> **rate limit:** 공개 repo는 토큰 없이 읽지만, GitHub 무인증 API는 시간당 60회 제한.
> 툴 콜링은 한 질문에 여러 번 위키를 읽으므로 60초 캐시를 둬서 같은 스냅샷을 재사용한다.
> 그래도 한도에 걸리면 `.env`의 `GITHUB_TOKEN=`에 읽기 전용 fine-grained PAT를 채우고
> 재배포하면 5000/시간.

## 3단계를 왜 한 덩어리로 만들었나

원래 계획은 3a(정리만) → 3b(PR) → 3c(👍 머지) → 3d(기존 노트 수정) 네 조각이었다.
쪼갠 이유는 "위키가 오염되면 되돌리는 데 사람 손이 든다"였는데, **PR 게이트를 세우는 순간
그 전제가 사라진다.** PR은 diff를 보여주고, 닫으면 완전한 취소다. 봇이 몰래 뭘 바꿀 수가 없다.

그러면 3a는 3b의 열등한 버전이 된다 — 같은 일을 하고 결과를 채팅에 뱉어 사람이 손으로 옮기게
만드는. 3d(기존 노트 수정)도 "새로 만드는 것보다 위험한 일"이 아니라 그냥 PUT에 sha를 하나
더 싣는 일이 된다. 위험 등급이 같아지니 순서를 매길 이유가 없다.

남은 건 3c(👍 머지)뿐인데, 그건 안전장치가 아니라 **편의 기능**이라 급하지 않다.

## 다음 단계

- **슬랙에 `.md` 파일 첨부로 던지기** — 지금은 멘션 본문 텍스트만 읽는다. `files:read` 스코프,
  `event.files[]` 파싱, `url_private`을 봇 토큰으로 GET. 파일 크기·확장자는 코드에서 막는다.
  붙여넣기 경로도 그대로 살려 둔다.
- **👍 리액션으로 머지** — `reactions:read` 스코프 + `reaction_added` 구독.
- **비용 레버** — 위 [비용](#비용)의 프롬프트 캐싱·규칙 문서 선적재. 감사 로그를 보고 결정.
- **검색 품질** — 한국어 조사 처리(`동시성을` → `동시성`), 별칭·태그 가중치 조정.
  브레인이 부르는 `search_wiki`가 이걸 쓰므로 평상시 답 품질도 같이 오른다.
- **MCP 분리(학습)** — `internal/wiki`를 별도 MCP 서버로 떼면 슬랙 봇뿐 아니라
  Claude 데스크톱에서도 같은 도구를 쓴다. 기능보다 MCP 구조를 익히는 게 목적.

## 안 바꾸는 규칙

1. **모델은 GitHub를 직접 만지지 않는다.** 정해진 툴만 부르고, 각 툴은 자기 인자를 코드에서 검증한다.
2. **권한 검사는 프롬프트가 아니라 코드로.** 프롬프트로 막은 것은 뚫린다고 가정한다.
3. **읽기 툴과 쓰기 툴은 분리한다.** 토큰도, 타입도.
4. **모든 쓰기는 미리보기 + 승인을 거친다.** PR이 그 미리보기고, 머지 API는 구현하지 않는다.
   `bot/` 브랜치 밖으로 나가는 커밋 경로도 없다.
5. **툴은 구조화된 JSON을 돌려주고, 말은 렌더 레이어가 만든다.**
6. **시크릿은 환경변수에만.** 코드에도 위키에도 두지 않는다.
